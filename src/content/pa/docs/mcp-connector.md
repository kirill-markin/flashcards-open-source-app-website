## Claude ਡਾਇਰੈਕਟਰੀ ਰਾਹੀਂ ਜੋੜੋ

[Claude ਡਾਇਰੈਕਟਰੀ ਵਿੱਚ Nibomo](https://claude.ai/directory/nibomo) ਖੋਲ੍ਹੋ, ਇਸ ਨੂੰ ਜੋੜੋ, ਆਪਣੇ Nibomo ਖਾਤੇ ਵਿੱਚ ਸਾਈਨ ਇਨ ਕਰੋ ਅਤੇ ਪਹੁੰਚ ਦੀ ਇਜਾਜ਼ਤ ਦਿਓ। Nibomo ਉੱਥੇ Community ਕਨੈਕਟਰ ਵਜੋਂ ਸੂਚੀਬੱਧ ਹੈ।

Claude Code ਲਈ ਉਹੀ Claude ਸਬਸਕ੍ਰਿਪਸ਼ਨ ਖਾਤਾ ਵਰਤੋ ਅਤੇ ਜੋੜਨ ਤੋਂ ਬਾਅਦ `/mcp` ਜਾਂਚੋ। API ਕੁੰਜੀ ਜਾਂ ਤੀਜੀ ਧਿਰ ਦੇ ਪ੍ਰੋਵਾਈਡਰ ਨਾਲ ਕੀਤੇ ਲੌਗ ਇਨ ਤੁਹਾਡੇ claude.ai ਕਨੈਕਟਰ ਆਪਣੇ-ਆਪ ਲੋਡ ਨਹੀਂ ਕਰਦੇ।

ਤੁਸੀਂ Claude Code ਨੂੰ ਸਿੱਧੇ ਤੌਰ ਉੱਤੇ ਵੀ ਕੌਂਫ਼ਿਗਰ ਕਰ ਸਕਦੇ ਹੋ। ਹੇਠਲੀ ਕਮਾਂਡ ਚਲਾਓ, ਫਿਰ Claude Code ਵਿੱਚ `/mcp` ਖੋਲ੍ਹੋ ਅਤੇ ਬ੍ਰਾਊਜ਼ਰ ਵਿੱਚ ਅਧਿਕਾਰ ਦੇਣ ਦੀ ਪ੍ਰਕਿਰਿਆ ਪੂਰੀ ਕਰੋ:

```bash
claude mcp add --transport http nibomo https://mcp.nibomo.com/mcp
```

[Claude Code MCP ਦਸਤਾਵੇਜ਼](https://code.claude.com/docs/en/mcp#use-mcp-servers-from-claudeai)।

## ਝਲਕ

Nibomo ਇੱਕ ਰਿਮੋਟ MCP (Model Context Protocol) ਸਰਵਰ ਚਲਾਉਂਦਾ ਹੈ, ਤਾਂ ਜੋ MCP ਕਲਾਇੰਟ ਅਤੇ
AI ਏਜੰਟ ਤੁਹਾਡੇ ਉਹ ਕਾਰਡ ਪੜ੍ਹ ਸਕਣ ਜਿਨ੍ਹਾਂ ਦੀ ਦੁਹਰਾਈ ਬਾਕੀ ਹੈ, ਤੁਹਾਡੇ ਨਾਲ ਇੱਕ-ਇੱਕ ਸਵਾਲ ਕਰਕੇ ਉਨ੍ਹਾਂ ਦੀ ਦੁਹਰਾਈ ਕਰ ਸਕਣ,
ਅਤੇ ਤੁਹਾਡੇ ਲਈ ਕਾਰਡ ਤੇ ਡੈੱਕ ਬਣਾ ਜਾਂ ਸੋਧ ਸਕਣ।

ਏਜੰਟ ਦੋ ਤਰੀਕਿਆਂ ਨਾਲ ਜੁੜ ਸਕਦੇ ਹਨ: ਇਸ MCP ਸਰਵਰ ਰਾਹੀਂ (Claude ਜਾਂ Cursor ਵਰਗੇ MCP ਕਲਾਇੰਟਾਂ
ਲਈ ਸਭ ਤੋਂ ਵਧੀਆ), ਜਾਂ CLI ਏਜੰਟਾਂ ਲਈ [Agents API ਡਿਸਕਵਰੀ URL](/docs/api/) ਰਾਹੀਂ।
ਦੋਵੇਂ ਹਰ ਵਰਤੋਂਕਾਰ ਦੇ ਆਪਣੇ ਡਾਟੇ ਵਾਲੇ ਉਸੇ ਇੰਟਰਫ਼ੇਸ ਤੱਕ ਪਹੁੰਚਦੇ ਹਨ; ਇਹ ਸਫ਼ਾ MCP ਸਰਵਰ ਬਾਰੇ ਹੈ।

ਇਸ ਨਾਲ ਇੱਥੇ ਜੁੜੋ:

```text
https://mcp.nibomo.com/mcp
```

ਟ੍ਰਾਂਸਪੋਰਟ Streamable HTTP ਹੈ। ਸਰਵਰ ਵਰਕਸਪੇਸ ਲੱਭਣ, ਕਾਰਡ ਅਤੇ ਡੈੱਕ ਪੜ੍ਹਨ ਤੇ ਲਿਖਣ, ਹਵਾਲਾ ਗਾਈਡਾਂ, ਦੁਹਰਾਈਆਂ ਅਤੇ ਖਾਤੇ ਦੀ ਵਰਤੋਂ ਲਈ ਅੱਠ ਟੂਲ ਦਿੰਦਾ ਹੈ।

## ਆਪਣੇ ਕਲਾਇੰਟ ਵਿੱਚ ਇਸ ਨੂੰ ਕਿਵੇਂ ਜੋੜਨਾ ਹੈ

ਜ਼ਿਆਦਾਤਰ ਕਲਾਇੰਟ ਰਿਮੋਟ MCP ਸਰਵਰ ਨੂੰ ਕਸਟਮ ਕਨੈਕਟਰ ਵਜੋਂ ਜੋੜਦੇ ਹਨ:

1. ਆਪਣੇ ਕਲਾਇੰਟ ਦੀਆਂ ਕਨੈਕਟਰ ਜਾਂ MCP ਸਰਵਰ ਸੈਟਿੰਗਾਂ ਖੋਲ੍ਹੋ।
2. ਇੱਕ ਕਸਟਮ ਕਨੈਕਟਰ ਜੋੜੋ ਅਤੇ ਸਰਵਰ URL `https://mcp.nibomo.com/mcp` ਪੇਸਟ ਕਰੋ।
3. ਇੰਟਰੈਕਟਿਵ ਕਲਾਇੰਟਾਂ ਵਿੱਚ, ਪੁੱਛੇ ਜਾਣ ਉੱਤੇ ਬ੍ਰਾਊਜ਼ਰ ਵਿੱਚ ਅਧਿਕਾਰ ਦਿਓ। ਸਰਵਰ
   Dynamic Client Registration ਵਾਲਾ OAuth 2.1 ਵਰਤਦਾ ਹੈ, ਇਸ ਲਈ ਨਾ ਕੋਈ ਕਲਾਇੰਟ ਸੀਕ੍ਰੇਟ
   ਪੇਸਟ ਕਰਨਾ ਪੈਂਦਾ ਹੈ ਅਤੇ ਨਾ ਹੀ ਪਹਿਲਾਂ ਕੋਈ ਐਪ ਰਜਿਸਟਰ ਕਰਨੀ ਪੈਂਦੀ ਹੈ।
4. ਹੈੱਡਲੈੱਸ ਜਾਂ CLI ਵਰਤੋਂ ਲਈ, ਬ੍ਰਾਊਜ਼ਰ ਪ੍ਰਵਾਹ ਦੀ ਥਾਂ ਆਪਣੀ ਏਜੰਟ API ਕੁੰਜੀ ਨਾਲ
   `Authorization: Bearer fca_…` ਹੈਡਰ ਸੈੱਟ ਕਰੋ।

ਅਧਿਕਾਰ ਦੇਣ ਤੋਂ ਬਾਅਦ, ਵਰਕਸਪੇਸ ਚੁਣਨ ਲਈ ਇੱਕ ਵਾਰ `list_workspaces` ਕਾਲ ਕਰੋ, ਫਿਰ
ਪੜ੍ਹਨ ਲਈ `sql_query` ਅਤੇ ਕਾਰਡਾਂ ਤੇ ਡੈੱਕਾਂ ਵਿੱਚ ਲਿਖਣ ਲਈ `sql_execute` ਵਰਤੋ। ਦੁਹਰਾਈ ਲਈ
`next_review_card`, ਫਿਰ `reveal_answer`, ਫਿਰ `submit_review` ਕਾਲ ਕਰੋ।

## ਟੂਲ

ਸਰਵਰ ਅੱਠ ਟੂਲ ਦਿੰਦਾ ਹੈ। ਪੜ੍ਹਨਾ ਅਤੇ ਲਿਖਣਾ ਜਾਣ-ਬੁੱਝ ਕੇ ਵੱਖ ਰੱਖੇ ਗਏ ਹਨ, ਤਾਂ ਜੋ ਕੋਈ ਇੱਕ
ਟੂਲ ਕਦੇ ਵੀ ਸੁਰੱਖਿਅਤ ਅਤੇ ਡਾਟਾ ਬਦਲਣ ਵਾਲੀਆਂ ਕਾਰਵਾਈਆਂ ਨੂੰ ਨਾ ਮਿਲਾਏ।

- `get_usage_limits` — ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਲਈ: ਖਾਤੇ ਦਾ ਪਲਾਨ, ਹੱਦਾਂ ਅਤੇ ਇਸ ਮਹੀਨੇ ਦੀ AI ਵਰਤੋਂ; ਇਹ ਕਾਰਡ ਨਾ ਪੜ੍ਹਦਾ ਹੈ ਅਤੇ ਨਾ ਬਦਲਦਾ ਹੈ।
- `sql_query` — ਤੁਹਾਡੇ ਕਾਰਡਾਂ ਅਤੇ ਡੈੱਕਾਂ ਤੱਕ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਵਾਲੀ ਪਹੁੰਚ (`SHOW TABLES`,
  `DESCRIBE`, `SHOW COLUMNS`, `SELECT`)।
- `sql_execute` — ਤੁਹਾਡੇ ਕਾਰਡਾਂ ਅਤੇ ਡੈੱਕਾਂ ਵਿੱਚ ਲਿਖਣ ਦੀ ਪਹੁੰਚ (`INSERT`, `UPDATE`,
  `DELETE`), ਇੱਕ ਐਟੌਮਿਕ ਬੈਚ ਵਜੋਂ।
- `list_workspaces` — ਤੁਹਾਡੀ ਪਹੁੰਚ ਵਾਲੇ ਵਰਕਸਪੇਸਾਂ ਦੀ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਵਾਲੀ ਸੂਚੀ,
  ਹਰ ਇੱਕ ਦੇ
  `workspaceId`, ਨਾਮ, ਸਰਗਰਮ ਕਾਰਡਾਂ ਦੀ ਗਿਣਤੀ, ਆਖ਼ਰੀ ਸਰਗਰਮੀ ਅਤੇ ਇਸ ਜਾਣਕਾਰੀ ਸਮੇਤ ਕਿ ਕੀ ਇਹ
  ਇਸ ਵੇਲੇ ਤੁਹਾਡਾ ਚੁਣਿਆ ਹੋਇਆ ਮੂਲ ਵਰਕਸਪੇਸ ਹੈ। SQL ਅਤੇ ਦੁਹਰਾਈ ਵਾਲੇ ਟੂਲਾਂ ਦੇ ਵਿਕਲਪਿਕ
  `workspaceId` ਆਰਗੂਮੈਂਟ ਲਈ ਵਾਪਸ ਮਿਲਿਆ `workspaceId` ਵਰਤੋ।
- `get_guide` — ਇੱਕ ਵਿਸ਼ੇ ਲਈ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਵਾਲੀ ਹਵਾਲਾ ਗਾਈਡ: `sql_dialect`,
  `card_authoring`, `bulk_authoring` ਜਾਂ `review_flow`। ਇਹ ਵਰਕਸਪੇਸ ਦਾ ਕੋਈ ਡਾਟਾ ਨਹੀਂ ਪੜ੍ਹਦਾ।
- `next_review_card` — ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਲਈ: ਦੁਹਰਾਈ ਲਈ ਅਗਲਾ ਕਾਰਡ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਸਿਰਫ਼
  ਮੂਹਰਲਾ ਪਾਸਾ, ਐਪਾਂ ਵਾਲੇ ਉਸੇ ਕਤਾਰ ਕ੍ਰਮ ਵਿੱਚ। ਵਿਕਲਪਿਕ `tags` ਜਾਂ `deckId` ਕਤਾਰ ਨੂੰ
  ਸੀਮਤ ਕਰਦਾ ਹੈ।
- `reveal_answer` — ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਲਈ: ਸਿੱਖਣ ਵਾਲੇ ਵੱਲੋਂ ਮੂਹਰਲੇ ਪਾਸੇ ਦਾ ਜਵਾਬ ਦੇਣ ਦੀ ਕੋਸ਼ਿਸ਼
  ਤੋਂ ਬਾਅਦ ਇੱਕ ਕਾਰਡ ਦਾ ਪਿਛਲਾ ਪਾਸਾ ਵਾਪਸ ਕਰਦਾ ਹੈ।
- `submit_review` — ਇੱਕ `Again`, `Hard`, `Good` ਜਾਂ `Easy` ਰੇਟਿੰਗ ਦਰਜ ਕਰਦਾ ਹੈ ਅਤੇ
  ਕਾਰਡ ਦੇ FSRS ਸ਼ਡਿਊਲ ਨੂੰ ਅੱਗੇ ਵਧਾਉਂਦਾ ਹੈ।

SQL ਇੰਟਰਫ਼ੇਸ ਜਾਣ-ਬੁੱਝ ਕੇ ਸੀਮਤ ਰੱਖਿਆ ਡਾਇਲੈਕਟ ਹੈ ਅਤੇ ਪੂਰਾ PostgreSQL ਨਹੀਂ ਹੈ।
ਇਹ ਦਸਤਾਵੇਜ਼ ਸਿਰਫ਼ ਸਮਰਥਿਤ ਡਾਇਲੈਕਟ ਬਾਰੇ ਹਨ, PostgreSQL ਨਾਲ ਅਨੁਕੂਲਤਾ ਦਾ
ਹਵਾਲਾ ਨਹੀਂ। ਸਟੇਟਮੈਂਟ ਸਿਰਫ਼ `workspace`, `cards`, `decks` ਅਤੇ
`review_events` ਰਿਸੋਰਸਾਂ ਨਾਲ ਕੰਮ ਕਰ ਸਕਦੇ ਹਨ, ਹਰ ਸਟੇਟਮੈਂਟ ਤੁਹਾਡੇ ਆਪਣੇ ਵਰਕਸਪੇਸ ਤੱਕ ਸੀਮਤ ਹੁੰਦਾ ਹੈ, ਅਤੇ
ਪੜ੍ਹਨ ਤੇ ਲਿਖਣ ਦੋਵਾਂ ਦੀ ਹੱਦ ਹਰ ਸਟੇਟਮੈਂਟ ਵਿੱਚ `100` ਕਤਾਰਾਂ ਹੈ।

## ਦੁਹਰਾਈਆਂ

ਦੁਹਰਾਈ ਵਾਲੇ ਟੂਲ ਏਜੰਟ ਨੂੰ ਸਿੱਖਣ ਵਾਲੇ ਤੋਂ ਇੱਕ ਵਾਰ ਵਿੱਚ ਇੱਕ ਕਾਰਡ ਪੁੱਛਣ ਅਤੇ ਹਰ
ਰੇਟਿੰਗ ਕਾਰਡ ਦੇ FSRS ਸ਼ਡਿਊਲ ਵਿੱਚ ਸੰਭਾਲਣ ਦਿੰਦੇ ਹਨ:

1. `next_review_card` ਇੱਕ `cardId` ਅਤੇ `frontText` ਵਾਪਸ ਕਰਦਾ ਹੈ, ਜਾਂ ਜਦੋਂ
   ਕਿਸੇ ਕਾਰਡ ਦੀ ਦੁਹਰਾਈ ਬਾਕੀ ਨਾ ਹੋਵੇ ਤਾਂ `card: null`।
2. ਸਿੱਖਣ ਵਾਲੇ ਦੇ ਜਵਾਬ ਦੇਣ ਤੋਂ ਬਾਅਦ, `reveal_answer` ਉਸ ਕਾਰਡ ਦਾ `backText` ਵਾਪਸ ਕਰਦਾ ਹੈ।
3. `submit_review` ਨੂੰ `cardId`, ਕਲਾਇੰਟ ਵੱਲੋਂ ਬਣਾਇਆ `reviewId` UUID, ਇੱਕ
   `rating`, ਅਤੇ ਸਿੱਖਣ ਵਾਲੇ ਦਾ IANA `reviewedTimeZone` ਦਿੱਤੇ ਜਾਂਦੇ ਹਨ। ਸਰਵਰ ਦੁਹਰਾਈ ਦਾ
   ਸਮਾਂ ਦਰਜ ਕਰਦਾ ਹੈ ਅਤੇ ਕਾਰਡ ਦਾ ਨਵਾਂ ਸ਼ਡਿਊਲ ਵਾਪਸ ਕਰਦਾ ਹੈ।

ਜੇ ਭੇਜਣ ਦੇ ਨਤੀਜੇ ਬਾਰੇ ਯਕੀਨ ਨਾ ਹੋਵੇ, ਤਾਂ ਉਸੇ `reviewId` ਨਾਲ ਦੁਬਾਰਾ ਭੇਜੋ; ਇਸ ਨਾਲ ਦੂਜੀ
ਦੁਹਰਾਈ ਕਦੇ ਦਰਜ ਨਹੀਂ ਹੁੰਦੀ। ਭੇਜਣ ਉੱਤੇ ਇਹ ਜਵਾਬ ਵੀ ਮਿਲ ਸਕਦੇ ਹਨ:

- `409 REVIEW_EVENT_CONFLICT` — ਦੁਹਰਾਈ ਪਹਿਲਾਂ ਹੀ ਦਰਜ ਹੋ ਚੁੱਕੀ ਹੈ, ਅਤੇ ਗਲਤੀ ਦੇ
  ਵੇਰਵਿਆਂ ਵਿੱਚ ਕਾਰਡ ਦਾ ਮੌਜੂਦਾ ਸ਼ਡਿਊਲ ਹੁੰਦਾ ਹੈ।
- `409 REVIEW_ID_CARD_MISMATCH` — ਇਹ `reviewId` ਪਹਿਲਾਂ ਹੀ ਕਿਸੇ ਹੋਰ ਕਾਰਡ ਦੀ ਦੁਹਰਾਈ ਦੀ
  ਪਛਾਣ ਵਜੋਂ ਵਰਤਿਆ ਜਾ ਚੁੱਕਾ ਹੈ, ਇਸ ਲਈ ਕੁਝ ਵੀ ਸੰਭਾਲਿਆ ਨਹੀਂ ਗਿਆ; ਨਵੇਂ `reviewId` ਨਾਲ ਦੁਬਾਰਾ ਭੇਜੋ।
- `409 REVIEW_STALE` — ਕਾਰਡ ਦਾ ਸੰਭਾਲਿਆ ਦੁਹਰਾਈ ਸਮਾਂ ਸਰਵਰ ਦੇ ਮੌਜੂਦਾ ਸਮੇਂ ਦੇ ਬਰਾਬਰ
  ਜਾਂ ਉਸ ਤੋਂ ਬਾਅਦ ਦਾ ਹੈ; ਕੋਈ ਹੋਰ ਕਾਰਡ ਦੁਹਰਾਓ।

ਦੁਹਰਾਈਆਂ ਸਿਰਫ਼ `submit_review` ਰਾਹੀਂ ਦਰਜ ਹੁੰਦੀਆਂ ਹਨ: SQL `review_events` ਜਾਂ
FSRS ਸ਼ਡਿਊਲਿੰਗ ਦੀ ਸਥਿਤੀ ਵਿੱਚ ਨਹੀਂ ਲਿਖ ਸਕਦਾ। ਦੁਹਰਾਈ ਅਤੇ ਰੇਟਿੰਗ ਦੇ ਪੂਰੇ ਨਿਯਮਾਂ ਲਈ
`review_flow` ਵਿਸ਼ੇ ਨਾਲ `get_guide` ਕਾਲ ਕਰੋ।

## ਕਾਰਡ ਦਾ ਕੰਟਰੈਕਟ

ਹਰ ਕਾਰਡ ਇੱਕੋ ਕੰਟਰੈਕਟ ਦੀ ਪਾਲਣਾ ਕਰਦਾ ਹੈ, ਅਤੇ ਟੂਲ ਇਸੇ ਉੱਤੇ ਨਿਰਭਰ ਕਰਦੇ ਹਨ:

- `front_text` ਸਿਰਫ਼ ਇੱਕ ਸਵਾਲ ਜਾਂ ਦੁਹਰਾਈ ਲਈ ਸੰਕੇਤ ਹੁੰਦਾ ਹੈ ਅਤੇ ਇਸ ਵਿੱਚ ਕਦੇ ਜਵਾਬ ਨਹੀਂ ਹੁੰਦਾ।
- `back_text` ਵਿੱਚ ਜਵਾਬ ਹੁੰਦਾ ਹੈ, ਲੋੜ ਹੋਵੇ ਤਾਂ ਇੱਕ ਠੋਸ ਮਿਸਾਲ ਸਮੇਤ।

`sql_execute` ਰਾਹੀਂ ਕਾਰਡ ਬਣਾਉਣ ਵਾਲੇ ਏਜੰਟ ਇਸ ਕੰਟਰੈਕਟ ਦੀ ਪਾਲਣਾ ਕਰਦੇ ਹਨ, ਇਸ ਲਈ ਉਨ੍ਹਾਂ ਦੇ
ਬਣਾਏ ਕਾਰਡ ਤੁਰੰਤ ਸਪੇਸਡ ਰਿਪੀਟੀਸ਼ਨ ਨਾਲ ਦੁਹਰਾਈ ਲਈ ਤਿਆਰ ਹੁੰਦੇ ਹਨ।

## ਪ੍ਰਮਾਣੀਕਰਨ

ਅਧਿਕਾਰ ਦੇਣ ਦੇ ਦੋਵੇਂ ਰਾਹ ਹਰ ਵਰਤੋਂਕਾਰ ਦੇ ਆਪਣੇ ਡਾਟੇ ਵਾਲੇ ਉਸੇ ਇੰਟਰਫ਼ੇਸ ਤੱਕ ਪਹੁੰਚਦੇ ਹਨ।

### OAuth 2.1 (ਇੰਟਰੈਕਟਿਵ ਕਨੈਕਟਰ ਕਲਾਇੰਟ)

ਸਰਵਰ PKCE ਅਤੇ Dynamic Client Registration ਨਾਲ authorization-code ਪ੍ਰਵਾਹ
ਲਾਗੂ ਕਰਦਾ ਹੈ। MCP URL ਨੂੰ ਕਸਟਮ ਕਨੈਕਟਰ ਵਜੋਂ ਜੋੜੋ ਅਤੇ ਬ੍ਰਾਊਜ਼ਰ ਵਿੱਚ ਅਧਿਕਾਰ ਦਿਓ;
ਕੋਈ ਕਲਾਇੰਟ ਸੀਕ੍ਰੇਟ ਪਹਿਲਾਂ ਤੋਂ ਸਾਂਝਾ ਨਹੀਂ ਕੀਤਾ ਜਾਂਦਾ। ਡਿਸਕਵਰੀ ਮਿਆਰੀ ਹੈ:

- ਸੁਰੱਖਿਅਤ ਰਿਸੋਰਸ ਦਾ ਮੈਟਾਡਾਟਾ:
  `https://mcp.nibomo.com/.well-known/oauth-protected-resource`
- ਅਧਿਕਾਰ ਸਰਵਰ ਦਾ ਮੈਟਾਡਾਟਾ:
  `https://auth.flashcards-open-source-app.com/.well-known/oauth-authorization-server`

### API ਕੁੰਜੀ (ਹੈੱਡਲੈੱਸ ਅਤੇ CLI ਵਰਤੋਂ)

[API ਹਵਾਲੇ](/docs/api/) ਵਿੱਚ ਦੱਸੇ ਈਮੇਲ OTP ਲੌਗ ਇਨ ਪ੍ਰਵਾਹ ਰਾਹੀਂ ਲੰਮੇ ਸਮੇਂ ਤੱਕ ਚੱਲਣ ਵਾਲੀ
`fca_` ਏਜੰਟ API ਕੁੰਜੀ ਲਓ, ਫਿਰ ਇਸ ਨੂੰ Bearer ਟੋਕਨ ਵਜੋਂ ਭੇਜੋ:

```text
Authorization: Bearer fca_ABCDEFGH_0123456789ABCDEFGHJKMNPQRS
```

ਇਹ ਉਹੀ ਕੁੰਜੀ ਹੈ ਜੋ REST ਏਜੰਟ ਇੰਟਰਫ਼ੇਸ ਸਵੀਕਾਰ ਕਰਦਾ ਹੈ, ਅਤੇ ਇਸ ਲਈ ਬ੍ਰਾਊਜ਼ਰ ਜਾਂ
OAuth ਵਾਲੇ ਗੇੜ ਦੀ ਲੋੜ ਨਹੀਂ।

ਦੋਵਾਂ ਰਾਹਾਂ ਦਾ ਅਧਿਕਾਰਤ, ਮਸ਼ੀਨ ਵੱਲੋਂ ਪੜ੍ਹਨਯੋਗ ਵੇਰਵਾ
`https://api.nibomo.com/v1/` ਉੱਤੇ ਮਿਲਦਾ ਡਿਸਕਵਰੀ ਪੇਲੋਡ ਹੈ (ਜਿਸ ਦੀ ਨਕਲ `/v1/agent` ਉੱਤੇ ਵੀ ਹੈ)।

## ਸੁਰੱਖਿਆ ਅਤੇ ਦਾਇਰਾ

SQL ਟੂਲਾਂ ਨੂੰ ਮਨਜ਼ੂਰੀ ਦੇਣਾ ਸੁਰੱਖਿਅਤ ਹੈ, ਕਿਉਂਕਿ ਇਹ ਇੰਟਰਫ਼ੇਸ ਡਾਟਾਬੇਸ ਤੱਕ ਮਨਮਰਜ਼ੀ ਦੀ ਪਹੁੰਚ ਨਹੀਂ,
ਸਗੋਂ ਸੀਮਤ ਦਾਇਰੇ ਵਾਲਾ ਡਾਇਲੈਕਟ ਹੈ, ਜਿਸ ਦੇ ਨਿਯਮ ਪਾਰਸਰ ਲਾਗੂ ਕਰਦਾ ਹੈ:

- **ਸਟੇਟਮੈਂਟਾਂ ਦੀ ਬੰਦ ਮਨਜ਼ੂਰ ਸੂਚੀ**: `sql_query` ਸਿਰਫ਼ `SHOW TABLES`,
  `DESCRIBE`, `SHOW COLUMNS` ਅਤੇ `SELECT` ਲੈਂਦਾ ਹੈ; `sql_execute` ਸਿਰਫ਼ `INSERT`,
  `UPDATE` ਅਤੇ `DELETE` ਲੈਂਦਾ ਹੈ। ਹੋਰ ਕੁਝ ਵੀ ਪਾਰਸ ਕਰਨ ਵੇਲੇ ਹੀ ਰੱਦ ਹੋ ਜਾਂਦਾ ਹੈ।
- **ਸੀਮਤ ਰਿਸੋਰਸ**: ਸਟੇਟਮੈਂਟ ਸਿਰਫ਼ `workspace`, `cards`, `decks`
  ਅਤੇ `review_events` ਤੱਕ ਪਹੁੰਚ ਸਕਦੇ ਹਨ।
- **ਹਰ ਵਰਕਸਪੇਸ ਤੱਕ ਸੀਮਤ ਦਾਇਰਾ**: ਹਰ SQL ਸਟੇਟਮੈਂਟ ਅਤੇ ਦੁਹਰਾਈ ਤੁਹਾਡੀ ਪਹੁੰਚ ਵਾਲੇ ਇੱਕ
  ਵਰਕਸਪੇਸ ਤੱਕ ਸੀਮਤ ਹੁੰਦੀ ਹੈ, ਜਾਂ ਤਾਂ ਤੁਹਾਡਾ ਦਿੱਤਾ `workspaceId` ਜਾਂ ਤੁਹਾਡਾ ਚੁਣਿਆ ਹੋਇਆ
  ਮੂਲ ਵਰਕਸਪੇਸ, ਅਤੇ ਦੂਜੇ ਵਰਕਸਪੇਸਾਂ (ਟੈਨੈਂਟਾਂ) ਤੱਕ ਕੋਈ ਪਹੁੰਚ ਨਹੀਂ ਹੁੰਦੀ।
- **ਸਖ਼ਤ ਆਰਗੂਮੈਂਟ**: ਹਰ ਟੂਲ ਕੋਈ ਵੀ ਅਣਜਾਣ ਆਰਗੂਮੈਂਟ ਰੱਦ ਕਰ ਦਿੰਦਾ ਹੈ, ਇਸ ਲਈ ਗਲਤ ਲਿਖਿਆ
  `workspaceId` ਤੁਹਾਡੇ ਮੂਲ ਵਰਕਸਪੇਸ ਉੱਤੇ ਚੱਲਣ ਦੀ ਥਾਂ ਫੇਲ੍ਹ ਹੋ ਜਾਂਦਾ ਹੈ।
- **ਹੱਦਾਂ**: ਹਰ ਸਟੇਟਮੈਂਟ ਵਿੱਚ ਵੱਧ ਤੋਂ ਵੱਧ `100` ਕਤਾਰਾਂ, ਹਰ ਬੈਚ ਵਿੱਚ ਵੱਧ ਤੋਂ ਵੱਧ `50` ਸਟੇਟਮੈਂਟ, ਅਤੇ
  ਨਤੀਜੇ ਦੀ ਹੱਦ ਲਗਭਗ `12k` ਟੋਕਨ। ਬਦਲਾਅ ਵਾਲੇ ਬੈਚ ਇਕੱਠੇ, ਐਟੌਮਿਕ ਤਰੀਕੇ ਨਾਲ ਲਾਗੂ ਹੁੰਦੇ ਹਨ।
- **ਪੜ੍ਹਨ ਅਤੇ ਲਿਖਣ ਦੀ ਵੰਡ**: `get_usage_limits`, `sql_query`, `list_workspaces`, `get_guide`,
  `next_review_card` ਅਤੇ `reveal_answer` ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਿਰਫ਼ ਪੜ੍ਹਨ ਲਈ ਹਨ (`readOnlyHint`)
  ਅਤੇ ਕਦੇ ਵੀ ਡਾਟਾ ਠੀਕ ਨਹੀਂ ਕਰਦੇ, ਸ਼ਡਿਊਲਿੰਗ ਦੁਬਾਰਾ ਨਹੀਂ ਗਿਣਦੇ ਜਾਂ ਕਾਰਡ ਦੀ ਸਥਿਤੀ ਨਹੀਂ ਬਦਲਦੇ।
  `sql_execute` ਅਤੇ `submit_review` ਹੀ ਲਿਖਣ ਵਾਲੇ ਟੂਲ ਹਨ (`destructiveHint`):
  `sql_execute` ਕਾਰਡਾਂ ਅਤੇ ਡੈੱਕਾਂ ਵਿੱਚ ਲਿਖਦਾ ਹੈ, ਅਤੇ `submit_review` ਦੁਹਰਾਈ ਦਰਜ ਕਰਦਾ ਹੈ ਅਤੇ
  ਉਸ ਕਾਰਡ ਦਾ ਸ਼ਡਿਊਲ ਅੱਗੇ ਵਧਾਉਂਦਾ ਹੈ।

ਪੂਰਾ ਸਟੈਕ — ਐਪ, ਬੈਕਐਂਡ ਅਤੇ ਬੁਨਿਆਦੀ ਢਾਂਚਾ — ਓਪਨ ਸੋਰਸ ਹੈ ਅਤੇ
[ਆਪ ਹੋਸਟ](/docs/self-hosting/) ਕੀਤਾ ਜਾ ਸਕਦਾ ਹੈ, ਇਸ ਲਈ ਤੁਸੀਂ ਇਹੀ ਕਨੈਕਟਰ ਆਪਣੀ
ਡਿਪਲੌਇਮੈਂਟ ਨਾਲ ਚਲਾ ਸਕਦੇ ਹੋ।

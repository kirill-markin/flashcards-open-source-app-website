## Claude డైరెక్టరీ ద్వారా కనెక్ట్ చేయండి

[Claude డైరెక్టరీలో Nibomo](https://claude.ai/directory/nibomo) ను తెరిచి, కనెక్ట్ చేసి, మీ Nibomo ఖాతాలో సైన్ ఇన్ చేసి, యాక్సెస్‌కు అనుమతి ఇవ్వండి. Nibomo అక్కడ Community కనెక్టర్‌గా జాబితాలో ఉంది.

Claude Code కోసం, అదే Claude సబ్‌స్క్రిప్షన్ ఖాతాను వాడి, కనెక్ట్ చేసిన తర్వాత `/mcp` ను తనిఖీ చేయండి. API కీతో లేదా మూడో పక్షం ప్రొవైడర్ ద్వారా చేసిన లాగిన్‌లు మీ claude.ai కనెక్టర్లను ఆటోమేటిక్‌గా లోడ్ చేయవు.

Claude Code ను నేరుగా కూడా కాన్ఫిగర్ చేయవచ్చు. కింది కమాండ్ నడిపి, ఆ తర్వాత Claude Code లో `/mcp` తెరిచి బ్రౌజర్‌లో అనుమతి ప్రక్రియను పూర్తి చేయండి:

```bash
claude mcp add --transport http nibomo https://mcp.nibomo.com/mcp
```

[Claude Code MCP డాక్యుమెంటేషన్](https://code.claude.com/docs/en/mcp#use-mcp-servers-from-claudeai).

## అవలోకనం

Nibomo ఒక రిమోట్ MCP (Model Context Protocol) సర్వర్‌ను నడుపుతుంది. దీని ద్వారా MCP క్లయింట్లు,
AI ఏజెంట్లు పునశ్చరణకు వచ్చిన మీ కార్డులను చదవగలవు, ఒక్కో ప్రశ్న చొప్పున మీతో కలిసి వాటిని పునశ్చరణ చేయగలవు,
మీ కోసం కార్డులు, డెక్‌లను సృష్టించగలవు లేదా సవరించగలవు.

ఏజెంట్లు రెండు విధాలుగా కనెక్ట్ కావచ్చు: ఈ MCP సర్వర్ ద్వారా (Claude, Cursor వంటి MCP క్లయింట్లకు
ఉత్తమం), లేదా CLI ఏజెంట్ల కోసం [Agents API డిస్కవరీ URL](/docs/api/) ద్వారా. రెండూ ఒకే
యూజర్ వారీ డేటా ఇంటర్‌ఫేస్‌ను చేరుకుంటాయి; ఈ పేజీ MCP సర్వర్ గురించి వివరిస్తుంది.

దీనికి ఇక్కడ కనెక్ట్ అవ్వండి:

```text
https://mcp.nibomo.com/mcp
```

ట్రాన్స్‌పోర్ట్ Streamable HTTP. సర్వర్ వర్క్‌స్పేస్‌లను కనుగొనడం, కార్డులు, డెక్‌లను చదవడం, రాయడం, రిఫరెన్స్ గైడ్‌లు, పునశ్చరణలు, ఖాతా వాడకం కోసం ఎనిమిది టూల్స్‌ను అందిస్తుంది.

## మీ క్లయింట్‌లో దీన్ని ఎలా జోడించాలి

చాలా క్లయింట్లు రిమోట్ MCP సర్వర్‌ను కస్టమ్ కనెక్టర్‌గా జోడిస్తాయి:

1. మీ క్లయింట్‌లోని కనెక్టర్ లేదా MCP సర్వర్ సెట్టింగ్‌లను తెరవండి.
2. కస్టమ్ కనెక్టర్‌ను జోడించి, సర్వర్ URL `https://mcp.nibomo.com/mcp` ను పేస్ట్ చేయండి.
3. ఇంటరాక్టివ్ క్లయింట్లలో, అడిగినప్పుడు బ్రౌజర్‌లో అనుమతి ఇవ్వండి. సర్వర్
   Dynamic Client Registration తో OAuth 2.1 ను వాడుతుంది, కాబట్టి పేస్ట్ చేయాల్సిన క్లయింట్ సీక్రెట్ గానీ
   ముందుగా నమోదు చేయాల్సిన యాప్ గానీ ఉండవు.
4. హెడ్‌లెస్ లేదా CLI వాడకం కోసం, బ్రౌజర్ ఫ్లోకు బదులుగా మీ ఏజెంట్ API కీతో
   `Authorization: Bearer fca_…` హెడర్‌ను సెట్ చేయండి.

అనుమతి ఇచ్చిన తర్వాత, వర్క్‌స్పేస్‌ను ఎంచుకోవడానికి ఒకసారి `list_workspaces` ను కాల్ చేయండి, ఆ తర్వాత
చదవడానికి `sql_query` ను, కార్డులు, డెక్‌లను రాయడానికి `sql_execute` ను వాడండి. పునశ్చరణ కోసం
`next_review_card`, ఆ తర్వాత `reveal_answer`, ఆ తర్వాత `submit_review` ను కాల్ చేయండి.

## టూల్స్

సర్వర్ ఎనిమిది టూల్స్‌ను అందిస్తుంది. ఏ ఒక్క టూల్ కూడా సురక్షితమైన, విధ్వంసక ఆపరేషన్‌లను
కలపకుండా ఉండేందుకు రీడ్‌లు, రైట్‌లను ఉద్దేశపూర్వకంగా వేరు చేశాం.

- `get_usage_limits` — ఖచ్చితంగా చదవడానికి మాత్రమే: ఖాతా ప్లాన్, పరిమితులు, ఈ నెల ప్రస్తుత AI వాడకం; ఇది కార్డులను చదవదు, మార్చదు.
- `sql_query` — మీ కార్డులు, డెక్‌లకు ఖచ్చితంగా చదవడానికి మాత్రమే యాక్సెస్ (`SHOW TABLES`,
  `DESCRIBE`, `SHOW COLUMNS`, `SELECT`).
- `sql_execute` — మీ కార్డులు, డెక్‌లకు రాసే యాక్సెస్ (`INSERT`, `UPDATE`,
  `DELETE`), ఒకే అటామిక్ బ్యాచ్‌గా.
- `list_workspaces` — ఖచ్చితంగా చదవడానికి మాత్రమే: మీకు యాక్సెస్ ఉన్న వర్క్‌స్పేస్‌ల జాబితా;
  ప్రతి దానికీ
  `workspaceId`, పేరు, యాక్టివ్ కార్డుల సంఖ్య, చివరి కార్యకలాపం, అది ప్రస్తుతం మీరు
  ఎంచుకున్న డిఫాల్టా కాదా అనే వివరాలు ఉంటాయి. SQL, పునశ్చరణ టూల్స్‌లోని ఐచ్ఛిక
  `workspaceId` ఆర్గ్యుమెంట్ కోసం తిరిగి వచ్చిన `workspaceId` ను వాడండి.
- `get_guide` — ఖచ్చితంగా చదవడానికి మాత్రమే: ఒక అంశంపై రిఫరెన్స్ గైడ్ (`sql_dialect`,
  `card_authoring`, `bulk_authoring` లేదా `review_flow`). ఇది ఏ వర్క్‌స్పేస్ డేటానూ చదవదు.
- `next_review_card` — ఖచ్చితంగా చదవడానికి మాత్రమే: పునశ్చరణ చేయాల్సిన తర్వాతి కార్డును, ముందు భాగం
  మాత్రమే, యాప్‌ల క్యూ క్రమంలోనే తిరిగి ఇస్తుంది. ఐచ్ఛిక `tags` లేదా `deckId`
  క్యూను పరిమితం చేస్తాయి.
- `reveal_answer` — ఖచ్చితంగా చదవడానికి మాత్రమే: అభ్యాసకుడు ముందు భాగానికి సమాధానం ప్రయత్నించిన
  తర్వాత ఒక కార్డు వెనుక భాగాన్ని తిరిగి ఇస్తుంది.
- `submit_review` — `Again`, `Hard`, `Good` లేదా `Easy` లో ఒక రేటింగ్‌ను నమోదు చేసి,
  కార్డు FSRS షెడ్యూల్‌ను ముందుకు జరుపుతుంది.

SQL ఇంటర్‌ఫేస్ ఉద్దేశపూర్వకంగా పరిమితం చేసిన డయలెక్ట్, పూర్తి PostgreSQL కాదు.
ఈ డాక్స్ మద్దతు ఉన్న డయలెక్ట్‌ను మాత్రమే వివరిస్తాయి; ఇవి PostgreSQL అనుకూలత
సూచిక కాదు. స్టేట్‌మెంట్‌లు `workspace`, `cards`, `decks`,
`review_events` రిసోర్సులను మాత్రమే సూచించగలవు, ప్రతి స్టేట్‌మెంట్ మీ సొంత వర్క్‌స్పేస్‌కే పరిమితం,
రీడ్‌లు, రైట్‌లు ఒక్కో స్టేట్‌మెంట్‌కు `100` వరుసలకు పరిమితం.

## పునశ్చరణలు

పునశ్చరణ టూల్స్‌తో ఏజెంట్ అభ్యాసకుడిని ఒక్కో కార్డుపై ప్రశ్నించి, ప్రతి
రేటింగ్‌ను కార్డు FSRS షెడ్యూల్‌లో సేవ్ చేయగలదు:

1. `next_review_card` ఒక `cardId`, `frontText` ను తిరిగి ఇస్తుంది; ఏదీ పునశ్చరణకు
   రాకపోతే `card: null` ఇస్తుంది.
2. అభ్యాసకుడు సమాధానం చెప్పిన తర్వాత, `reveal_answer` ఆ కార్డు `backText` ను తిరిగి ఇస్తుంది.
3. `submit_review` `cardId`, క్లయింట్ రూపొందించిన `reviewId` UUID, ఒక
   `rating`, అభ్యాసకుడి IANA `reviewedTimeZone` ను తీసుకుంటుంది. సర్వర్
   పునశ్చరణ సమయాన్ని నమోదు చేసి, కార్డు కొత్త షెడ్యూల్‌ను తిరిగి ఇస్తుంది.

సమర్పణ జరిగిందో లేదో అనిశ్చితంగా ఉంటే, అదే `reviewId` తో మళ్లీ ప్రయత్నించండి; అలా చేసినా రెండో
పునశ్చరణ ఎప్పుడూ నమోదు కాదు. సమర్పణకు ఈ స్పందనలు కూడా రావచ్చు:

- `409 REVIEW_EVENT_CONFLICT` — పునశ్చరణ ఇప్పటికే నమోదైంది, ఎర్రర్
  వివరాల్లో కార్డు ప్రస్తుత షెడ్యూల్ ఉంటుంది.
- `409 REVIEW_ID_CARD_MISMATCH` — `reviewId` ఇప్పటికే వేరే కార్డు పునశ్చరణను
  సూచిస్తోంది, కాబట్టి ఏదీ సేవ్ కాలేదు; కొత్త `reviewId` తో మళ్లీ సమర్పించండి.
- `409 REVIEW_STALE` — కార్డులో నిల్వ ఉన్న పునశ్చరణ సమయం ప్రస్తుత
  సర్వర్ సమయానికి సమానంగా లేదా దాని తర్వాత ఉంది; వేరే కార్డును పునశ్చరణ చేయండి.

పునశ్చరణలు `submit_review` ద్వారా మాత్రమే నమోదవుతాయి: SQL
`review_events` ను గానీ FSRS షెడ్యూలింగ్ స్థితిని గానీ రాయలేదు. పూర్తి పునశ్చరణ, రేటింగ్ నియమాల కోసం
`review_flow` అంశంతో `get_guide` ను కాల్ చేయండి.

## కార్డు కాంట్రాక్ట్

ప్రతి కార్డు ఒకే కాంట్రాక్ట్‌ను పాటిస్తుంది, టూల్స్ దానిపై ఆధారపడతాయి:

- `front_text` లో ప్రశ్న లేదా పునశ్చరణ ప్రాంప్ట్ మాత్రమే ఉంటుంది; అందులో ఎప్పుడూ సమాధానం ఉండదు.
- `back_text` లో సమాధానం ఉంటుంది, కావాలంటే ఒక నిర్దిష్ట ఉదాహరణతో పాటు.

`sql_execute` ద్వారా కార్డులు రూపొందించే ఏజెంట్లు ఈ కాంట్రాక్ట్‌ను పాటిస్తాయి, కాబట్టి
అవి సృష్టించే కార్డులను వెంటనే స్పేస్‌డ్ రిపిటిషన్‌తో పునశ్చరణ చేయవచ్చు.

## ప్రామాణీకరణ

రెండు అనుమతి మార్గాలు ఒకే యూజర్ వారీ డేటా ఇంటర్‌ఫేస్‌ను చేరుకుంటాయి.

### OAuth 2.1 (ఇంటరాక్టివ్ కనెక్టర్ క్లయింట్లు)

సర్వర్ PKCE, Dynamic Client Registration తో authorization-code ఫ్లోను
అమలు చేస్తుంది. MCP URL ను కస్టమ్ కనెక్టర్‌గా జోడించి బ్రౌజర్‌లో అనుమతి ఇవ్వండి;
క్లయింట్ సీక్రెట్‌ను ముందుగా పంచుకోవాల్సిన అవసరం లేదు. డిస్కవరీ ప్రామాణిక పద్ధతిలోనే ఉంటుంది:

- ప్రొటెక్టెడ్-రిసోర్స్ మెటాడేటా:
  `https://mcp.nibomo.com/.well-known/oauth-protected-resource`
- ఆథరైజేషన్-సర్వర్ మెటాడేటా:
  `https://auth.flashcards-open-source-app.com/.well-known/oauth-authorization-server`

### API కీ (హెడ్‌లెస్, CLI)

[API సూచిక](/docs/api/) లో వివరించిన ఈమెయిల్ OTP లాగిన్ ఫ్లో ద్వారా దీర్ఘకాల `fca_` ఏజెంట్ API కీని
పొందండి, ఆపై దాన్ని Bearer టోకెన్‌గా పంపండి:

```text
Authorization: Bearer fca_ABCDEFGH_0123456789ABCDEFGHJKMNPQRS
```

REST ఏజెంట్ ఇంటర్‌ఫేస్ అంగీకరించే కీ ఇదే; దీనికి బ్రౌజర్ గానీ
OAuth రౌండ్-ట్రిప్ గానీ అవసరం లేదు.

రెండు మార్గాల అధికారిక, మెషీన్ చదవగలిగే వివరణ `https://api.nibomo.com/v1/` వద్ద ఉన్న
డిస్కవరీ పేలోడ్ (`/v1/agent` వద్ద కూడా ఇదే ఉంది).

## భద్రత, పరిధి

SQL టూల్స్‌ను ఆమోదించడం సురక్షితం, ఎందుకంటే ఈ ఇంటర్‌ఫేస్ ఎలాంటి పరిమితులూ లేని డేటాబేస్ యాక్సెస్ కాదు;
ఇది పార్సర్ అమలు చేసే, పరిమితమైన డయలెక్ట్:

- **నిర్ణీత స్టేట్‌మెంట్ అనుమతి జాబితా**: `sql_query` `SHOW TABLES`,
  `DESCRIBE`, `SHOW COLUMNS`, `SELECT` ను మాత్రమే అంగీకరిస్తుంది; `sql_execute` `INSERT`,
  `UPDATE`, `DELETE` ను మాత్రమే అంగీకరిస్తుంది. మిగతా ఏదైనా పార్సింగ్ దశలోనే తిరస్కరించబడుతుంది.
- **పరిమిత రిసోర్సులు**: స్టేట్‌మెంట్‌లు `workspace`, `cards`, `decks`,
  `review_events` ను మాత్రమే తాకగలవు.
- **వర్క్‌స్పేస్ వారీ పరిధి**: ప్రతి SQL స్టేట్‌మెంట్, ప్రతి పునశ్చరణ మీకు యాక్సెస్ ఉన్న ఒక్క
  వర్క్‌స్పేస్‌కే పరిమితం, అది మీరు పంపిన `workspaceId` అయినా లేదా మీరు ఎంచుకున్న
  డిఫాల్ట్ అయినా; ఒక టెనెంట్ నుంచి మరో టెనెంట్ డేటాకు యాక్సెస్ ఉండదు.
- **కఠినమైన ఆర్గ్యుమెంట్‌లు**: ప్రతి టూల్ తెలియని ఆర్గ్యుమెంట్‌ను తిరస్కరిస్తుంది, కాబట్టి తప్పుగా రాసిన
  `workspaceId` మీ డిఫాల్ట్ వర్క్‌స్పేస్‌పై నడవకుండా విఫలమవుతుంది.
- **పరిమితులు**: ఒక్కో స్టేట్‌మెంట్‌కు గరిష్ఠంగా `100` వరుసలు, ఒక్కో బ్యాచ్‌కు గరిష్ఠంగా `50` స్టేట్‌మెంట్‌లు,
  ఫలితానికి సుమారు `12k` టోకెన్ల పరిమితి. మార్పుల బ్యాచ్‌లు అటామిక్‌గా వర్తిస్తాయి.
- **రీడ్/రైట్ విభజన**: `get_usage_limits`, `sql_query`, `list_workspaces`, `get_guide`,
  `next_review_card`, `reveal_answer` ఖచ్చితంగా చదవడానికి మాత్రమే (`readOnlyHint`);
  అవి ఎప్పుడూ డేటాను సరిచేయవు, షెడ్యూలింగ్‌ను తిరిగి లెక్కించవు, కార్డు స్థితిని మార్చవు.
  `sql_execute`, `submit_review` మాత్రమే రైట్ టూల్స్ (`destructiveHint`):
  `sql_execute` కార్డులు, డెక్‌లను రాస్తుంది, `submit_review` ఒక పునశ్చరణను నమోదు చేసి
  దాని కార్డు షెడ్యూల్‌ను ముందుకు జరుపుతుంది.

మొత్తం స్టాక్ — యాప్, బ్యాకెండ్, మౌలిక సదుపాయాలు — ఓపెన్ సోర్స్, దాన్ని
[సొంతంగా హోస్ట్ చేయవచ్చు](/docs/self-hosting/), కాబట్టి ఇదే కనెక్టర్‌ను మీ
సొంత డిప్లాయ్‌మెంట్‌పై నడపవచ్చు.

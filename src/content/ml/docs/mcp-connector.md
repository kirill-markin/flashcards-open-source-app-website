## Claude ഡയറക്ടറി വഴി ബന്ധിപ്പിക്കുക

[Claude ഡയറക്ടറിയിലെ Nibomo](https://claude.ai/directory/nibomo) തുറന്ന് ബന്ധിപ്പിക്കുക, നിങ്ങളുടെ Nibomo അക്കൗണ്ടിൽ സൈൻ ഇൻ ചെയ്യുക, ആക്സസിന് അനുമതി നൽകുക. Nibomo ഒരു Community കണക്ടറായാണ് ലിസ്റ്റ് ചെയ്തിരിക്കുന്നത്.

Claude Code ൽ, അതേ Claude സബ്സ്ക്രിപ്ഷൻ അക്കൗണ്ട് ഉപയോഗിക്കുക, ബന്ധിപ്പിച്ച ശേഷം `/mcp` പരിശോധിക്കുക. API കീ ഉപയോഗിച്ചോ മൂന്നാം കക്ഷി ദാതാവ് വഴിയോ ഉള്ള ലോഗിനുകൾ നിങ്ങളുടെ claude.ai കണക്ടറുകൾ സ്വയമേവ ലോഡ് ചെയ്യുന്നില്ല.

Claude Code നേരിട്ടും കോൺഫിഗർ ചെയ്യാം. താഴെയുള്ള കമാൻഡ് പ്രവർത്തിപ്പിക്കുക, തുടർന്ന് Claude Code ൽ `/mcp` തുറന്ന് ബ്രൗസറിലെ അനുമതി പ്രക്രിയ പൂർത്തിയാക്കുക:

```bash
claude mcp add --transport http nibomo https://mcp.nibomo.com/mcp
```

[Claude Code MCP രേഖകൾ](https://code.claude.com/docs/en/mcp#use-mcp-servers-from-claudeai).

## അവലോകനം

MCP ക്ലയന്റുകൾക്കും AI ഏജന്റുകൾക്കും നിങ്ങൾ ആവർത്തിക്കേണ്ട കാർഡുകൾ വായിക്കാനും, ഓരോ ചോദ്യമായി നിങ്ങളോടൊപ്പം
അവ ആവർത്തിക്കാനും, നിങ്ങൾക്കായി കാർഡുകളും ഡെക്കുകളും ഉണ്ടാക്കാനും തിരുത്താനും കഴിയുന്നതിനായി
Nibomo ഒരു റിമോട്ട് MCP (Model Context Protocol) സെർവർ പ്രവർത്തിപ്പിക്കുന്നു.

ഏജന്റുകൾക്ക് രണ്ട് വഴികളിൽ ബന്ധിപ്പിക്കാം: ഈ MCP സെർവർ വഴി (Claude അല്ലെങ്കിൽ Cursor പോലുള്ള
MCP ക്ലയന്റുകൾക്ക് ഏറ്റവും അനുയോജ്യം), അല്ലെങ്കിൽ CLI ഏജന്റുകൾക്കായി [Agents API ഡിസ്കവറി URL](/docs/api/) വഴി.
രണ്ടും ഒരേ ഉപയോക്തൃ-നിർദ്ദിഷ്ട ഡാറ്റാ സർഫേസിലാണ് എത്തുന്നത്; ഈ പേജ് MCP സെർവറിനെക്കുറിച്ചാണ്.

ഈ വിലാസത്തിൽ ബന്ധിപ്പിക്കുക:

```text
https://mcp.nibomo.com/mcp
```

ട്രാൻസ്പോർട്ട് Streamable HTTP ആണ്. വർക്ക്‌സ്‌പേസ് കണ്ടെത്തൽ, കാർഡുകളുടെയും ഡെക്കുകളുടെയും റീഡും റൈറ്റും, റഫറൻസ് വഴികാട്ടികൾ, ആവർത്തനങ്ങൾ, അക്കൗണ്ട് ഉപയോഗം എന്നിവയ്ക്കായി സെർവർ എട്ട് ടൂളുകൾ ലഭ്യമാക്കുന്നു.

## നിങ്ങളുടെ ക്ലയന്റിൽ ഇത് എങ്ങനെ ചേർക്കാം

മിക്ക ക്ലയന്റുകളും ഒരു റിമോട്ട് MCP സെർവർ കസ്റ്റം കണക്ടറായാണ് ചേർക്കുന്നത്:

1. നിങ്ങളുടെ ക്ലയന്റിന്റെ കണക്ടർ അല്ലെങ്കിൽ MCP സെർവർ ക്രമീകരണങ്ങൾ തുറക്കുക.
2. ഒരു കസ്റ്റം കണക്ടർ ചേർത്ത് സെർവർ URL `https://mcp.nibomo.com/mcp` പേസ്റ്റ് ചെയ്യുക.
3. ഇന്ററാക്ടീവ് ക്ലയന്റുകളിൽ, ആവശ്യപ്പെടുമ്പോൾ ബ്രൗസറിൽ അനുമതി നൽകുക. സെർവർ
   Dynamic Client Registration ഉള്ള OAuth 2.1 ഉപയോഗിക്കുന്നു, അതിനാൽ പേസ്റ്റ് ചെയ്യേണ്ട ക്ലയന്റ് സീക്രട്ടോ
   മുൻകൂട്ടി രജിസ്റ്റർ ചെയ്യേണ്ട ആപ്പോ ഇല്ല.
4. ഹെഡ്‌ലെസ് അല്ലെങ്കിൽ CLI ഉപയോഗത്തിന്, ബ്രൗസർ പ്രക്രിയയ്ക്കു പകരം നിങ്ങളുടെ ഏജന്റ് API കീ ഉപയോഗിച്ച്
   `Authorization: Bearer fca_…` ഹെഡർ സജ്ജമാക്കുക.

അനുമതി നൽകിയ ശേഷം, ഒരു വർക്ക്‌സ്‌പേസ് തിരഞ്ഞെടുക്കാൻ `list_workspaces` ഒരിക്കൽ വിളിക്കുക, തുടർന്ന്
റീഡുകൾക്ക് `sql_query` ഉം കാർഡ്, ഡെക്ക് റൈറ്റുകൾക്ക് `sql_execute` ഉം ഉപയോഗിക്കുക. ആവർത്തിക്കാൻ,
`next_review_card`, തുടർന്ന് `reveal_answer`, തുടർന്ന് `submit_review` എന്നിവ വിളിക്കുക.

## ടൂളുകൾ

സെർവർ എട്ട് ടൂളുകൾ ലഭ്യമാക്കുന്നു. ഒരു ടൂളും സുരക്ഷിതമായ പ്രവർത്തനങ്ങളും വിനാശകരമായ പ്രവർത്തനങ്ങളും
ഒരുമിച്ച് കലർത്താതിരിക്കാൻ റീഡുകളും റൈറ്റുകളും മനഃപൂർവം വേർതിരിച്ചിരിക്കുന്നു.

- `get_usage_limits` — കർശനമായി റീഡ്-ഒൺലി: അക്കൗണ്ട് പ്ലാൻ, പരിധികൾ, ഈ മാസത്തെ നിലവിലെ AI ഉപയോഗം; ഇത് കാർഡുകൾ വായിക്കുകയോ മാറ്റുകയോ ചെയ്യുന്നില്ല.
- `sql_query` — നിങ്ങളുടെ കാർഡുകളിലേക്കും ഡെക്കുകളിലേക്കും കർശനമായി റീഡ്-ഒൺലി ആക്സസ് (`SHOW TABLES`,
  `DESCRIBE`, `SHOW COLUMNS`, `SELECT`).
- `sql_execute` — നിങ്ങളുടെ കാർഡുകളിലേക്കും ഡെക്കുകളിലേക്കും ഒരു അറ്റോമിക് ബാച്ചായി റൈറ്റ് ആക്സസ് (`INSERT`, `UPDATE`,
  `DELETE`).
- `list_workspaces` — നിങ്ങൾക്ക് ആക്സസ് ഉള്ള വർക്ക്‌സ്‌പേസുകളുടെ കർശനമായി റീഡ്-ഒൺലി പട്ടിക,
  ഓരോന്നിനും
  `workspaceId`, പേര്, സജീവ കാർഡുകളുടെ എണ്ണം, അവസാന പ്രവർത്തനം, അത് നിലവിൽ നിങ്ങൾ
  തിരഞ്ഞെടുത്ത ഡിഫോൾട്ട് ആണോ എന്നിവ സഹിതം. SQL, ആവർത്തന ടൂളുകളുടെ ഐച്ഛികമായ `workspaceId` ആർഗ്യുമെന്റിനായി
  ലഭിക്കുന്ന ഒരു `workspaceId` ഉപയോഗിക്കുക.
- `get_guide` — ഒരു വിഷയത്തിനുള്ള കർശനമായി റീഡ്-ഒൺലി റഫറൻസ് വഴികാട്ടി: `sql_dialect`,
  `card_authoring`, `bulk_authoring`, അല്ലെങ്കിൽ `review_flow`. ഇത് വർക്ക്‌സ്‌പേസ് ഡാറ്റയൊന്നും വായിക്കുന്നില്ല.
- `next_review_card` — കർശനമായി റീഡ്-ഒൺലി: ആവർത്തിക്കേണ്ട അടുത്ത കാർഡ്, മുൻവശം
  മാത്രം, ആപ്പുകളിലെ അതേ ക്യൂ ക്രമത്തിൽ നൽകുന്നു. ഐച്ഛികമായ `tags` അല്ലെങ്കിൽ `deckId` ക്യൂ
  ചുരുക്കുന്നു.
- `reveal_answer` — കർശനമായി റീഡ്-ഒൺലി: പഠിതാവ് മുൻവശത്തിന് ഉത്തരം നൽകാൻ ശ്രമിച്ച ശേഷം ഒരു കാർഡിന്റെ
  പിൻവശം നൽകുന്നു.
- `submit_review` — `Again`, `Hard`, `Good`, അല്ലെങ്കിൽ `Easy` എന്നിവയിൽ ഒരു റേറ്റിംഗ് രേഖപ്പെടുത്തുകയും
  കാർഡിന്റെ FSRS ഷെഡ്യൂൾ മുന്നോട്ട് നീക്കുകയും ചെയ്യുന്നു.

SQL സർഫേസ് മനഃപൂർവം പരിമിതപ്പെടുത്തിയ ഒരു ഡയലക്റ്റാണ്, പൂർണ്ണമായ PostgreSQL അല്ല.
ഈ രേഖകൾ പിന്തുണയുള്ള ഡയലക്റ്റ് മാത്രമാണ് വിവരിക്കുന്നത്, PostgreSQL അനുയോജ്യതാ
റഫറൻസ് അല്ല. സ്റ്റേറ്റ്മെന്റുകൾക്ക് `workspace`, `cards`, `decks`,
`review_events` എന്നീ റിസോഴ്സുകൾ മാത്രമേ ഉപയോഗിക്കാനാകൂ, ഓരോ സ്റ്റേറ്റ്മെന്റും നിങ്ങളുടെ സ്വന്തം വർക്ക്‌സ്‌പേസിലേക്ക് പരിമിതപ്പെടുത്തിയിരിക്കുന്നു,
റീഡുകൾക്കും റൈറ്റുകൾക്കും ഒരു സ്റ്റേറ്റ്മെന്റിന് `100` വരികളാണ് പരമാവധി.

## ആവർത്തനങ്ങൾ

ആവർത്തന ടൂളുകൾ ഒരു ഏജന്റിന് പഠിതാവിനോട് ഓരോ കാർഡായി ചോദ്യങ്ങൾ ചോദിക്കാനും ഓരോ
റേറ്റിംഗും കാർഡിന്റെ FSRS ഷെഡ്യൂളിലേക്ക് സംരക്ഷിക്കാനും അവസരം നൽകുന്നു:

1. `next_review_card` ഒരു `cardId` ഉം `frontText` ഉം നൽകുന്നു, അല്ലെങ്കിൽ ആവർത്തിക്കാൻ
   ഒന്നുമില്ലെങ്കിൽ `card: null`.
2. പഠിതാവ് ഉത്തരം നൽകിയ ശേഷം, `reveal_answer` ആ കാർഡിന്റെ `backText` നൽകുന്നു.
3. `submit_review` `cardId`, ക്ലയന്റ് സൃഷ്ടിച്ച ഒരു `reviewId` UUID, ഒരു
   `rating`, പഠിതാവിന്റെ IANA `reviewedTimeZone` എന്നിവ സ്വീകരിക്കുന്നു. സെർവർ
   ആവർത്തന സമയം രേഖപ്പെടുത്തുകയും കാർഡിന്റെ പുതിയ ഷെഡ്യൂൾ നൽകുകയും ചെയ്യുന്നു.

ഫലം ഉറപ്പില്ലാത്ത ഒരു സമർപ്പണം അതേ `reviewId` ഉപയോഗിച്ച് വീണ്ടും ശ്രമിക്കുക; അത് ഒരിക്കലും രണ്ടാമതൊരു
ആവർത്തനം രേഖപ്പെടുത്തില്ല. ഒരു സമർപ്പണത്തിന് ഇങ്ങനെയും മറുപടി ലഭിക്കാം:

- `409 REVIEW_EVENT_CONFLICT` — ആവർത്തനം ഇതിനകം രേഖപ്പെടുത്തിയിട്ടുണ്ട്, പിശകിന്റെ
  വിശദാംശങ്ങളിൽ കാർഡിന്റെ നിലവിലെ ഷെഡ്യൂൾ ഉണ്ട്.
- `409 REVIEW_ID_CARD_MISMATCH` — `reviewId` ഇതിനകം മറ്റൊരു കാർഡിന്റെ
  ആവർത്തനത്തെ സൂചിപ്പിക്കുന്നു, അതിനാൽ ഒന്നും സംരക്ഷിച്ചില്ല; പുതിയൊരു `reviewId` ഉപയോഗിച്ച് വീണ്ടും സമർപ്പിക്കുക.
- `409 REVIEW_STALE` — കാർഡിന്റെ സംരക്ഷിച്ച ആവർത്തന സമയം നിലവിലെ
  സെർവർ സമയത്തിന് തുല്യമോ അതിന് ശേഷമോ ആണ്; മറ്റൊരു കാർഡ് ആവർത്തിക്കുക.

ആവർത്തനങ്ങൾ `submit_review` വഴി മാത്രമേ രേഖപ്പെടുത്തൂ: SQL ന്
`review_events` ലേക്കോ FSRS ഷെഡ്യൂളിംഗ് നിലയിലേക്കോ എഴുതാൻ കഴിയില്ല. ആവർത്തനത്തിന്റെയും റേറ്റിംഗിന്റെയും
പൂർണ്ണ നിയമങ്ങൾക്കായി `review_flow` എന്ന വിഷയത്തോടെ `get_guide` വിളിക്കുക.

## കാർഡ് കരാർ

ഓരോ കാർഡും ഒരേ കരാർ പിന്തുടരുന്നു, ടൂളുകൾ അതിനെ ആശ്രയിക്കുന്നു:

- `front_text` ഒരു ചോദ്യമോ ആവർത്തനത്തിനുള്ള സൂചനയോ മാത്രമാണ്, ഒരിക്കലും ഉത്തരം ഉൾക്കൊള്ളുന്നില്ല.
- `back_text` ഉത്തരം ഉൾക്കൊള്ളുന്നു, വേണമെങ്കിൽ ഒരു മൂർത്തമായ ഉദാഹരണവും.

`sql_execute` വഴി കാർഡുകൾ ഉണ്ടാക്കുന്ന ഏജന്റുകൾ ഈ കരാർ പിന്തുടരുന്നു, അതിനാൽ അവ ഉണ്ടാക്കുന്ന
കാർഡുകൾ ഉടൻതന്നെ സ്പേസ്ഡ് റിപ്പറ്റീഷൻ ഉപയോഗിച്ച് ആവർത്തിക്കാൻ തയ്യാറാണ്.

## ഓതന്റിക്കേഷൻ

രണ്ട് അനുമതി വഴികളും ഒരേ ഉപയോക്തൃ-നിർദ്ദിഷ്ട ഡാറ്റാ സർഫേസിലാണ് എത്തുന്നത്.

### OAuth 2.1 (ഇന്ററാക്ടീവ് കണക്ടർ ക്ലയന്റുകൾ)

സെർവർ PKCE ഉം Dynamic Client Registration ഉം ഉള്ള authorization-code ഫ്ലോ
നടപ്പാക്കുന്നു. MCP URL ഒരു കസ്റ്റം കണക്ടറായി ചേർത്ത് ബ്രൗസറിൽ അനുമതി നൽകുക;
ഒരു ക്ലയന്റ് സീക്രട്ടും മുൻകൂട്ടി പങ്കിടുന്നില്ല. ഡിസ്കവറി സ്റ്റാൻഡേർഡ് രീതിയിലാണ്:

- സംരക്ഷിത റിസോഴ്സ് മെറ്റാഡാറ്റ:
  `https://mcp.nibomo.com/.well-known/oauth-protected-resource`
- ഓതറൈസേഷൻ സെർവർ മെറ്റാഡാറ്റ:
  `https://auth.flashcards-open-source-app.com/.well-known/oauth-authorization-server`

### API കീ (ഹെഡ്‌ലെസ്, CLI)

[API റഫറൻസിൽ](/docs/api/) വിവരിച്ചിരിക്കുന്ന ഇമെയിൽ OTP ലോഗിൻ പ്രക്രിയയിലൂടെ ഒരു ദീർഘകാല `fca_` ഏജന്റ് API കീ
നേടുക, തുടർന്ന് അത് ഒരു Bearer ടോക്കണായി അയയ്ക്കുക:

```text
Authorization: Bearer fca_ABCDEFGH_0123456789ABCDEFGHJKMNPQRS
```

REST ഏജന്റ് സർഫേസ് സ്വീകരിക്കുന്ന അതേ കീയാണിത്, ഇതിന് ബ്രൗസറോ
OAuth റൗണ്ട്-ട്രിപ്പോ ആവശ്യമില്ല.

രണ്ട് വഴികളുടെയും ഔദ്യോഗികവും മെഷീന് വായിക്കാവുന്നതുമായ വിവരണം
`https://api.nibomo.com/v1/` ലെ ഡിസ്കവറി പേലോഡാണ് (`/v1/agent` ൽ അതിന്റെ പകർപ്പുണ്ട്).

## സുരക്ഷയും പരിധിയും

SQL ടൂളുകൾക്ക് അനുമതി നൽകുന്നത് സുരക്ഷിതമാണ്, കാരണം ഈ സർഫേസ് ഡാറ്റാബേസിലേക്കുള്ള
നിയന്ത്രണമില്ലാത്ത ആക്സസ് അല്ല, പാർസർ നിയന്ത്രിക്കുന്ന, പരിധിക്കുള്ളിൽ ഒതുങ്ങുന്ന ഒരു ഡയലക്റ്റാണ്:

- **അടച്ച സ്റ്റേറ്റ്മെന്റ് അനുമതിപ്പട്ടിക**: `sql_query` `SHOW TABLES`,
  `DESCRIBE`, `SHOW COLUMNS`, `SELECT` എന്നിവ മാത്രം സ്വീകരിക്കുന്നു; `sql_execute` `INSERT`,
  `UPDATE`, `DELETE` എന്നിവ മാത്രം സ്വീകരിക്കുന്നു. മറ്റെന്തും പാർസ് ചെയ്യുന്ന ഘട്ടത്തിൽ തന്നെ നിരസിക്കപ്പെടും.
- **പരിമിതമായ റിസോഴ്സുകൾ**: സ്റ്റേറ്റ്മെന്റുകൾക്ക് `workspace`, `cards`, `decks`,
  `review_events` എന്നിവയിൽ മാത്രമേ പ്രവർത്തിക്കാനാകൂ.
- **ഓരോ വർക്ക്‌സ്‌പേസിലേക്കുമുള്ള പരിധി**: ഓരോ SQL സ്റ്റേറ്റ്മെന്റും ആവർത്തനവും നിങ്ങൾക്ക് ആക്സസ് ഉള്ള ഒരു
  വർക്ക്‌സ്‌പേസിലേക്ക് പരിമിതപ്പെടുത്തിയിരിക്കുന്നു, നിങ്ങൾ നൽകുന്ന `workspaceId` അല്ലെങ്കിൽ നിങ്ങൾ തിരഞ്ഞെടുത്ത
  ഡിഫോൾട്ട്; മറ്റ് ടെനന്റുകളുടെ ഡാറ്റയിലേക്ക് ആക്സസ് ഇല്ല.
- **കർശനമായ ആർഗ്യുമെന്റുകൾ**: ഓരോ ടൂളും അറിയാത്ത ആർഗ്യുമെന്റ് നിരസിക്കുന്നു, അതിനാൽ അക്ഷരത്തെറ്റുള്ള
  `workspaceId` നിങ്ങളുടെ ഡിഫോൾട്ട് വർക്ക്‌സ്‌പേസിൽ പ്രവർത്തിക്കുന്നതിനു പകരം പരാജയപ്പെടുന്നു.
- **പരിധികൾ**: ഒരു സ്റ്റേറ്റ്മെന്റിന് പരമാവധി `100` വരികൾ, ഒരു ബാച്ചിൽ പരമാവധി `50` സ്റ്റേറ്റ്മെന്റുകൾ,
  ഏകദേശം `12k` ടോക്കണുകളുടെ ഫല പരിധി. മാറ്റം വരുത്തുന്ന ബാച്ചുകൾ അറ്റോമിക്കായി പ്രയോഗിക്കുന്നു.
- **റീഡ്/റൈറ്റ് വിഭജനം**: `get_usage_limits`, `sql_query`, `list_workspaces`, `get_guide`,
  `next_review_card`, `reveal_answer` എന്നിവ കർശനമായി റീഡ്-ഒൺലിയാണ് (`readOnlyHint`),
  അവ ഒരിക്കലും ഡാറ്റ നന്നാക്കുകയോ ഷെഡ്യൂളിംഗ് വീണ്ടും കണക്കാക്കുകയോ കാർഡിന്റെ നില മാറ്റുകയോ ചെയ്യുന്നില്ല.
  `sql_execute`, `submit_review` എന്നിവ മാത്രമാണ് റൈറ്റ് ടൂളുകൾ (`destructiveHint`):
  `sql_execute` കാർഡുകളും ഡെക്കുകളും എഴുതുന്നു, `submit_review` ഒരു ആവർത്തനം രേഖപ്പെടുത്തുകയും
  അതിന്റെ കാർഡിന്റെ ഷെഡ്യൂൾ മുന്നോട്ട് നീക്കുകയും ചെയ്യുന്നു.

മുഴുവൻ സ്റ്റാക്കും — ആപ്പ്, ബാക്കെൻഡ്, ഇൻഫ്രാസ്ട്രക്ചർ — ഓപ്പൺ സോഴ്സ് ആണ്, അത്
[സ്വന്തമായി ഹോസ്റ്റ് ചെയ്യാം](/docs/self-hosting/), അതിനാൽ ഇതേ കണക്ടർ നിങ്ങളുടെ
സ്വന്തം ഡിപ്ലോയ്മെന്റുമായി ബന്ധിപ്പിച്ച് ഉപയോഗിക്കാം.
